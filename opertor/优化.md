# 背景知识

## 1. DMA层（HBM <--> LDM访存）
```bash 
1. 是什么
DMA是横在HBM和LDM之间的独立的搬运引擎

软件填一张描述符，告诉DMA从哪搬运数据，搬运到哪，以及搬运多少数据

计算单元(ACE/SIMD)只读写LDM，接触不到HBM，所有的数据的进出都是靠DMA。

rt_dma_iget：搬连续的块
rt_dma_iget_stride：搬固定步长的块

2. 损耗在哪
T1没有人体地址列表一次提交的gather描述符：随机indices[]散布的数据只能逐条rt_dma_iget

前端/描述符开销：每张描述符都要issue(引擎解析排队) + reply(完成通知)，成本和描述符张数相关，与要搬运的字节数无关

小记录 + 大量记录时，命令开销该国实际传输带宽，DMA卡在收命令而非搬数据


> 说明：
> 1. rt_dma_iget、rt_dma_iget_strid是两个函数
> 2. indices[]里面存储的是整数编号，告诉DMA第i个要取的目标，是源数据在第几号记录，如，indices[i]是一个普通的数字，含义就是我要的第i个结果，对应HBM源数据里第indices[i]号固定记录大小
真正的源地址：源地址 = base + indices[i] * record_bytes。base 是整块数据的起点，record_bytes 是每条记录大小，indices[i] 是这条记录在第几格。
> 3. 前端(Front-end)--DMA引擎里收命令并解析的硬件。DMA 引擎不是一接命令就搬，它内部有专门接收和解析描述符的硬件模块，叫前端。前端负责：接收这张描述符、解析字段（src/dst/len/stride/reply）、排进引擎内部的队列；
> 4. issue —— "把描述符交给引擎"这个动作，是个动作。issue 是动词/动作，指软件提交（下发）一张 DMA 描述符给引擎前端。
> 5. 这里的软件就是我们写的kernal函数，就是那个.scpp
> 6. 算子 = kernel + 外面的host调度/参数封装/测试


3. 如何优化
减描述符张数（命令开销型瓶颈）：连续用 iget，等步长用 iget_stride，相邻递增记录用 pair-stride-gather 合成一次 stride（32→~21 张）。
双缓冲 / ping-pong：DMA 搬下一块时 ACE 算当前块，隐藏传输延迟。
复用 / 常驻：A 跨 N 复用、B row-ring 共享、LDM/表常驻，从源头少搬。
先 benchmark 确认瓶颈是 issue/reply（减描述符）还是带宽（换复用/重叠）。
```


## 2. RMA层(核间通信/32 SPE组)

```bash

1. 是什么
RMA是SPE<-->SPE的片上互联引擎，就是一个SPE的LDM到另一个SPE的LDM，核间直传。
负责跨核传数据：split-K 的 C quarter 规约、B panel row-ring 转发、QK/SV 跨核搬运。与 DMA 是不同引擎，但同样有"提交描述符 + 完成通知"模型。异步完成字必须用 __rt_local_rply / __rt_remote_rply。


2. 损耗在哪
命令开销：提交/完成 RMA 描述符，∝ 请求数（同 DMA）。
互联争用：32 SPE 共享片上网络，RMA 越多越拥堵。
缓冲占用：收方要在 LDM 留 receive buffer 并管所有权，挤占 LDM。
过度拆分反亏：把 partial O 拆多笔 RMA，描述符+reply 开销超过重叠收益（chunked-rma-merge-request-overhead）。
round 不足摊不薄：persistent 通信固定开销要靠足够多轮 query 摊薄（persistent-query-small-round-overhead）。


3. 如何优化
减 RMA 请求数：同列只 exchange 必要 quarter，不广播。
合并收发、规划好缓冲所有权与 reply/wait。
保证 round 数足够大再上 persistent；避免无收益拆分。
与 pipeline 配合：ACE 消费后立即 issue RMA 转发，避免与 C reduce reply 冲突。
```

## 3. ACE层(矩阵计算单元)

```bash

1. 是什么
ACE是核内做矩阵乘专用的计算单元(硬件电路)：A走west、B走north喂入，C写回LDM。

> 说明：
> 1. "A 走 west、B 走 north 喂入" 是什么? ACE 的两个进料口在物理布局上的方向
> 2. MAC数：Multiply-Accumulate（乘加）。矩阵乘的本质就是海量 MAC——C 的每个元素都是一串 Σ a·b，也就是一串 MAC。ACE 里并排摆了很多个 MAC 单元，每个周期（每拍时钟）所有 MAC 同时做一次乘加。所以：
ACE 算力 ≈ MAC 数量 × 每拍次数 × 时钟频率
        ≈ (MAC数) × 2 × 频率       （1 个 MAC = 1 次乘 + 1 次加 = 2 FLOP）

拍 = 一个时钟周期（clock cycle），是硬件的心跳。频率 1 GHz 就是每秒 10⁹ 拍。每个拍，所有电路同步动一次。


2. 损耗在哪
喂不饱（starvation）：ACE 等 LDM 的 A/B，DMA 没及时供数 → 空转。
填不满（under-occupancy）：M tile 太小，ACE west 宽度没用满（ace-west-mtile-occupancy）。
重复搬运 A：同一 A tile 扫多个 N panel 时反复 HBM load。
split-K 反噬：K 拆到多 row 后每 SPE 只有 partial C，必须 RMA reduce 才正确（带来 RMA 开销）。
写回争用：ACE 写 C 与后续 SIMD/更新抢 LDM 与通路。


3. 怎么优化
双缓冲供数（ab-dma-double-buffer-ace-gemm）消除 starvation。
调 M2/N2/K2/K3 提占用（a-reuse-across-n 让 A 只 load 一次；b-row-ring-panel-sharing 多列共享 B）。
2D split-K + C RMA reduce 换核占用（70.5→54.6ms），但需配套 RMA 安全。
ACE 写回与 SIMD 重叠（ace-writeback-simd-update-overlap）。

```
| 因子 | 含义 | 例子 |
| :--- | :--- | :--- |
| **MAC 数量** | ACE 里并排多少个“乘加单元”，能同时干活 | 1024 个 |
| **每拍次数** | 每个 MAC 每拍能做几次乘加（通常 1 次） | 1 MAC/拍 |
| **时钟频率** | 每秒多少拍 | 1 GHz = 10⁹ 拍/秒 |



## 4. SIMD层(向量计算/epilogue)

```bash

1. 是什么
SIMD 是核内向量计算单元，跑 softmax / reduce / cast / activation / epilogue 等。靠 floatv16 等向量寄存器和 simd_concat/max/exp 等指令做并行。


2. 损耗在哪
标量热循环：32-lane 的 max/sum 用标量循环，没用向量树形归约，慢。
无效重扫：running max 不变时仍重扫输出 accumulator。
重复 LDM 流量：先写 fp32 概率到 LDM，下游 ACE 再转 half，二次转换+多一次 LDM 读写。
独立 finalize pass：单独 O /= run_sum 全量扫描，浪费一遍。
展开度拍脑袋：固定 8x 可能寄存器爆或依赖距离不符，反而回退（反例 c-quarter-reduce-fp32）。


3. 怎么优化
Online Softmax Tile Microkernel：reduce_32<IS_MAX> 树形归约取代标量循环；max 不变跳过 rescale；exp_and_pack_to_half 直接出 half；final-divide 融合进最后 SV chunk（534→288ms）。
*C quarter reduce (fp32)*：split-K 本地 partial C 向量规约，按展开度/对齐/tail/寄存器压力实测。
向量 exp 查表 + 8x 展开替换标量 expf。
fp16 widen compute：窄 elementwise 先 widen 到 fp32 算再 narrow 回，兼顾精度吞吐。
红线：展开度按依赖距离/对齐/寄存器压力实测选 4x/8x，不固定。
```


## 5. LDM层(片上buffer规划)

```bash

1. 是什么
LDM 是每个 SPE 私有的片上 scratchpad（软件显式管理的小块高速内存），是 ACE/SIMD 唯一直接访问的内存。所有 HBM 数据必须经 DMA 进 LDM 才能被计算。


2. 损耗在哪
buffer 不够 / ownership 混乱：producer/consumer 归属不清，next DMA 覆盖当前 ACE 正读的 buffer → 精度失败或回退。
bank 争用：DMA 与 ACE 抢同一 LDM bank → 性能回退且无 bank 重排则无解。
重复搬运：数据不常驻，每次重新 DMA 进 LDM。
容量超预算：双缓冲/M2 增大后 LDM 爆，被迫降配。


3. 怎么优化
ping/pong 双缓冲：A/B 各两 buffer + 两 reply slot，curr=kt&1/next=curr^1，wait 卡消费者而非紧跟生产者。
明确 ownership，next DMA 绝不写当前被读的 buffer；避开同 bank 争用。
常驻：长 prefill 让 LDM/表常驻，跨 query 复用（persistent attention）。
设计文档同步写清 ldm_planning / double_buffer_strategy / pipeline_layout。

```

## 6. Workspace 层

```bash

1. 是什么
Workspace 是 HBM 上的一块临时暂存区，用于核间/跨 macro-tile 的中间结果交换——典型是 split-K 的 partial C 不便走 RMA 时，先写 workspace，最后统一 reduce。


2. 损耗在哪
额外 HBM 往返：partial C 写 workspace 再读回，多一次 HBM 流量。
ownership 混乱：partial layout 与 C double buffer 混在一起引入写覆盖/读脏 bug。
与 RMA reduce 选择错误：能用 RMA 规约的硬走 workspace，白白多 HBM 开销。


3. 怎么优化
明确 partial C 的 layout 与 ownership，单独 attempt 验证。
能走 RMA reduce 就走 RMA（更快，片上）；只有跨 macro-tile 或 fused epilogue 改变所有权时才用 workspace。
与 C double buffer 严格隔离，避免缓冲重叠。
```

## 7. Pipline层

```bash

1. 是什么
Pipeline 是把"DMA 搬数 / ACE 计算 / RMA 通信 / SIMD epilogue"四件事在时间上重叠起来的调度艺术，分 fill（预热）/ steady（稳态重叠）/ drain（收尾）三段，核心是决定 wait/sync 点放在哪。


2. 损耗在哪
串行化：DMA → wait → 计算 → wait → 通信 全串行，一段卡住后面全停。
wait 太早：issue next DMA 后立刻 wait，退化成串行 DMA/ACE。
reply 未重置：复用 reply slot 前不清零，wait_value 看到旧值。
冲突：B 转发 RMA 与 C reduce reply 抢通路。
固定开销摊不薄：persistent / 双缓冲的 drain 固定成本在 round 数少时占比过高。


3. 怎么优化
A/B DMA 双缓冲喂 ACE：预取 K0，每轮 wait 当前、立刻 issue next、再算当前，隐藏 DMA 延迟（72.85→70.54ms，单点收益有限，需配 A 复用）。
ACE writeback 与 SIMD 重叠：wait 点移到第一消费点。
B row-ring 转发与 ACE 重叠：ACE 消费后立即 issue RMA 转发 B，避开 C reduce reply。
跨 query persistent：长 prefill 让 LDM/表常驻，Q 预取与输出 wait 跨 query 延迟。
online-softmax partial state tree merge：decode split-K 时 partial max/sum/O 共同合并。
热路径 specialization 隔离：prefill/decode 共享模板时隔离热路径，A/B 验证布局收益。

```



launch 不是免费的，它包含一段固定成本，和 kernel 内部算多少无关：
1. host 侧驱动把这次执行提交进命令队列；
2. 设备收到命令、调度、把 kernel 加载/启动到 SPE；
3. 通常还要一次同步（host 等设备算完，或设备通知 host）。
这笔成本是"每次 launch 都固定收一次"，跟 kernel 里面是算 1 个数还是算 10 亿个数关系不大。


Host 优化方向清单
1. 减 launch 次数（最猛的一刀）
launch 每次都白交固定启动费，所以核心是"少发几次"。
- persistent kernel：一次 launch 处理连续多个 token / query（如 cross-query-persistent-attention），把"每 token 一 launch"变"一次 launch 干一片" → 直接降 TPOT；
- 注意坑：persistent-query-small-round-overhead——round 数太少时 fixed 开销摊不薄，反而亏，要凑够轮次才上。
- 算子融合：把多个小算子合成一个 kernel，少几次 host 派发。
2. 预分配 / 复用资源
- workspace、KV cache、中间 buffer 启动时预分配一次，调用间复用；
- 严禁每次调用都 malloc/free——分配器开销在高频调用下累积成 host 瓶颈。
3. 缓存决策（避免重复算）
- 相同 shape 的 find() 分块结果（ROWS/COLS/M2/N2/K2）缓存，别每次调用重跑选择逻辑；
- 常量参数（网格布局、tile 数）算一次传下去。
4. 精简参数打包
- Args 只填必要字段，结构体对齐，避免冗余拷贝；
- 能在 host 预先算好的（偏移、网格映射）算一次，不让 kernel 反复重算。
5. 避免多余同步
- 非必要不在 host 侧 wait，让设备流水跑完由框架统一同步；
- 过早同步会打断 pipeline，让计算被切碎。
6. 批量聚合（框架层）
- 把多个小请求 batch 成一个大调用，让 host 固定开销被大 tensor 摊薄。
怎么判断该用哪条
端到端慢，但 [Hardware Time] 低？
├── 是 → host 在拖，按上面清单查：
│     ├── decode/TPOT 高        → 方向1（persistent / 融合）
│     ├── 分配/释放频繁         → 方向2（预分配）
│     ├── 同 shape 反复 find    → 方向3（缓存）
│     └── 每步都 wait           → 方向5（去同步）
└── 否 → 别动 host，回去攻 kernel 7 层






























现实：文档里的优化几乎全是 device 侧
前面那 7 层（DMA/RMA/ACE/SIMD/LDM/Workspace/Pipeline）全都跑在 SPE 设备上，因为算子 99% 的时间花在设备计算上。学到的 learned-patterns 也全是设备机制——host 优化在知识库里基本是空白。
但 host 侧确实能成为瓶颈，只是触发条件更窄。
什么时候 host 会成为瓶颈
host 接口/调度做的事：解析参数、算 tiling 策略（find）、打包 Args、申请 workspace、RUN_KERNEL 启动 kernel、同步结果。这些对大 tensor 来说一次搞定、成本可忽略。但以下情况 host 开销会"显形"：
场景	host 瓶颈表现
shape 很小 / 调用极频繁	每次调用都重复 find() 选分支、打包参数、launch——launch 延迟和 host 逻辑占比升高，变成 "launch-bound"
每次调用都 malloc workspace	反复在 host 申请/释放显存，分配器开销累积
find() 重复算同一决策	相同 shape 每次都重跑分支选择逻辑
CPU 侧多余同步	不必要地 wait 阻塞 host，打断流水
参数打包低效	拷了多余字段、结构体没对齐、重复拷贝
host 能怎么优化（按收益排序）
1. 减少 launch 次数（最大的杠杆）
- 用 persistent kernel（如 cross-query-persistent-attention）：一次 launch 处理连续多个 query/chunk，把"每小块一次启动"压成"一次启动干一大片"——既减设备 drain 开销，也直接减 host 的 launch 次数。
- 算子融合：把多个小算子合成一个 kernel，少几次 host 派发。
2. 缓存决策与资源
- 相同 shape 的 find() 结果缓存，不每次重算；
- workspace / buffer 预分配并复用，别每次调用现申请。
3. 精简参数打包
- Args 只填必要字段，结构体对齐，避免冗余拷贝；
- 把 host 能预先算好的常量（如 tile 数、网格 ROWS×COLS）算一次传下去。
4. 避免多余同步
- 非必要不在 host 侧 wait；让设备流水跑完再由框架统一同步。
5. 分摊到更大批次
- 框架层把多个小请求 batch 成一个大调用，让 host 固定开销被大 tensor 摊薄。
怎么判断该不该优化 host
用 benchmark 看设备时间 vs 端到端时间：
- 设备 [Average Hardware Time] 很低、但框架测的 wall-clock 明显更高 → host/launch 开销大，该优化 host（减 launch、缓存、复用）。
- 设备时间本身就高 → 老老实实优化 device 那 7 层，host 再怎么调也救不了。
一句话
可以优化 host，但优先级低于 device；host 优化主要是"减 launch 次数、缓存决策、复用资源、精简打包"，只在小 shape / 高频调用 / 重复分配时才显出收益。文档体系里的优化知识几乎全在 device 侧，host 优化是补漏而非主攻方向。

























# 算子的项目目录结构

```bash

(host)  interface/ops/rms_norm.cpp                  对外契约：用户/PyTorch/Plugin 调用的稳定 C API；只组装 Args、调 RUN_OP

(host)  ual/args/rms_norm_args.h                    数据契约：host→device 的载荷，被 interface、ops、kernel 三方共享

(host)  ual/ops/rms_norm/find_rms_norm.cpp          分支派发/策略：按 data_type/algo 选具体 kernel

(kernel)  ual/kernel/rms_norm/*.scpp                设备计算

(host)  test/zoo/teco/rms_norm/*                    验收：CPU 参考实现，与 kernel 对拍


相互作用：
1. interface：
interface 是给用户/PyTorch 绑定/Plugin 的公开契约（tecoopsRmsNorm(handle, input, weight, …)）。优化时你会疯狂改 kernel、加分支、换算法——但只要不改签名，调用方一行都不用动。把"对外接口"单独锁在一个目录，就是为了内部随便重构、外部零影响。

2. args
RmsNormArgs 里集中定义了 shape、dtype、指针、flag（has_residual）。interface 填它、ops 读它、kernel 用它在 device 上取数。如果参数定义散在 interface 里，将来加一个 gamma 或 beta 就得改三处还容易不一致。独立成 args/ 让"算子有哪些参数"只有一个地方可查。

3. ops
findRmsNormBranch() 只有 6 行：按 has_residual 返回 0（纯 RMSNorm）或 1（带 residual）。注意 这两个 kernel 已经在 ual/kernel/ 里写好了，ops 层只做"选哪个"。好处：
- 新增一个 TECOOPS_ALGO_1（比如 bf16 版）→ 只需加一个 kernel + 在 findRmsNormBranch 多一个分支，不碰 interface、不碰测试、不碰 args。
- 多个 dtype/多个 algo 能映射到不同 kernel，而公开 API 不变。这就是 technique-teco-ops-interface-ual-layering 说的 findImpl()/setInstance() 绑定函数指针。

4. kernel
在设备上进行计算的

总体的流程：
interface----> 数据(args)----> 策略(选择kernel)----> 计算(kernel)----> 验收(test)
上层只依赖下层的稳定接口，下层随便换实现


args 是被包含/使用的类型；ops 是被 RUN_OP 宏间接调用；kernel 是被 ops.run 通过 <<<>>> 发射启动——三者都不是"在 interface 源码里直接逐行调用"。interface 文件里你真正能看到的调用只有 checkRmsNormInput 和 RUN_OP 这两处，其余都藏在 RUN_OP 展开之后。


RUN_OP 不是"第六层"，而是嵌在 interface 层里的接线员：它本身在 interface 文件里，但一展开就替 interface 去调了"策略层"的 find 和"计算层"的 run。所以你看到的分层流程，正是 RUN_OP 这个宏在运行时实际走完的路径——分层是设计，RUN_OP 是把设计落地的那根线。

```

# 算子优化

> 算子的优化主要就是访存瓶颈和计算瓶颈

1. DMA
```bash

1. 是什么
DMA（Direct Memory Access）是 SDAA 里数据搬运的专用通道，负责这几条路径（同一 SPA 内）：
- Global ↔ SPM（最常用：HBM 高带宽存储 ↔ 片上存储）
- Global ↔ Global（同 SPA 内）
- SPM ↔ SPM（同一 SPE 内）
注意：跨 SPE 的 SPM↔SPM 不走 DMA，要走 RMA / Broadcast（这是后面会讲的另一种机制）。

2. 两类 DMA：阻塞 vs 非阻塞（性能分水岭）
            接口	                                             特点
阻塞型	    memcpy / memcpy_stride / check_memcpy	            搬完才能执行下一条指令；简单但性能差
非阻塞型	memcpy_async / memcpy_wait / MemcpyHandle           搬运期间 CPU/SPE 可继续算别的东西；复杂但性能好
关键约束（memcpy_async）：
- 只支持 Global ↔ SPM，不支持 SPM↔SPM、Global↔Global、跨 SPE 的 SPM。
- 地址需 4B 对齐，size 是 4B 整数倍。
- stride 跨步只能在 Global 侧设置（SPM 侧不支持跨步单元）。
- 阻塞型 memcpy 做 Global↔Global 时会临时占用 20KB SPM 堆做中转——能避则避。

```

```bash

DMA的瓶颈分析：

一、DMA 瓶颈的两副面孔（都属于访存屋顶）
- 带宽型：HBM↔SPM 的搬运量超过 DMA 带宽，计算单元饿着等数据。
- 延迟型：单次搬运耗时里，计算在空转（没和计算重叠）。
优化 DMA 主要打延迟型——用非阻塞 + 双缓冲把延迟藏掉；带宽型则要靠减搬运量（tiling/复用/Broadcast）。

二、六类具体 DMA 瓶颈
1. 阻塞型串行（最基础）
用 memcpy / memcpy_async 后立刻 memcpy_wait，每轮"搬完才算、算完再搬"，计算单元在 DMA 期间完全空转。性能手册明确：阻塞型"使用简单，但性能不佳"。这是入门级 DMA 瓶颈。

2. 双缓冲但 wait 位置错 → 重叠没建起来
ab-dma-double-buffer-ace-gemm pattern 指出：发完 next DMA 立刻 wait next 会退化回串行——等于白做双缓冲。正确做法是"wait 当前块 → 立刻发下一块 → 当前块去算"，wait 必须卡消费者而非生产者。这是"想重叠却没重叠成"的典型瓶颈。

3. SPE ID 余数冲突（DMA 硬件资源争用）
性能手册 4.2.2 实测：用 8 个 SPE 组做 DMA，性能取决于 SPE_ID % 8 的余数是否分散：
- A={0..7}（余数全不同）最好
- B={0,1,2,3,8,9,10,11}（2 组同余）次之
- C={0,1,8,9,16,17,24,25}（4 组同余）最差
即"相同余数的 SPE 数量尽可能小"。这是 DMA 引擎/通道层面的硬件争用瓶颈——不是带宽也不是延迟，而是多个 SPE 在抢同一 DMA 资源。优化时要刻意选余数分散的线程组。

4. LDM 容量 → 被迫缩小 K2（优化引发二次瓶颈）
这是最反直觉的 DMA 瓶颈，ab-double-buffer-k2-regression 失败案例：
- 加 A/B 双缓冲需 2×A + 2×B + C + RMA缓冲 + 累加缓冲，LDM 放不下，被迫把 K2 从 512 缩到 256/416。
- K2 变小 → K 方向 macro 迭代变多 → 放大了 C 的 RMA reduce + HBM C 读改写流量，反而更慢：
- 基线 K2=512 单缓冲：54.6ms
- K2=256 双缓冲：61.3ms（回退）
- K2=416 双缓冲：56.0ms（仍回退）
- 教训：DMA 双缓冲不是默认必赢；它改善的是 DMA 延迟，但若以牺牲 K2、放大 C 侧流量为代价，会触发另一类（计算/访存）瓶颈。这正是"DMA 优化引发二次瓶颈"——属于我前面说的"资源约束"类。

5. 对齐 / 跨步约束
- 地址需 4B 对齐、size 是 4B 整数倍，否则失败或降级。
- stride 跨步只能在 Global 侧设，SPM 侧不支持；非连续访问受限。
- 阻塞 memcpy 做 Global↔Global 会临时占 20KB SPM 堆做中转——挤占本就紧张的 LDM。

6. 机制用错（跨核想用 DMA）
DMA 不支持：SPM↔SPM（同核）、Global↔Global（非阻塞）、跨 SPE 的 SPM。跨核数据必须走 RMA / Broadcast。若在一个本该 RMA 的场景硬用 DMA，是根本性错误（编译/运行不支持或性能崩）。这也是"DMA 瓶颈"的一种——用错了搬运通道。

三、怎么判断 DMA 是不是瓶颈、是哪种
按这个顺序定位（对应前面"访存/计算受限"的诊断）：
1. 先定性：对比理论带宽上限 vs 实测搬运量；若接近 → 带宽型（只能减搬运量）。
2. 看重叠：把 memcpy_wait 前后加计时，若计算和 DMA 时间相加而非重叠 → 延迟型、流水没建起（查 wait 位置 / 双缓冲 ownership）。
3. 查硬件争用：多 SPE 时查 SPE_ID % 8 分布，必要时换线程组。
4. 查资源反噬：加双缓冲/大 tile 后若 LDM 吃紧、K2/分块被迫缩小 → 算 C 侧/访存次生平 traffic，回到第 1 步重评。
5. 查约束违规：对齐、跨步、机制选择是否踩红线。
```

2. SIMD

```bash

1. 是什么
SIMD = Single Instruction Multiple Data（单指令多数据）：一条指令同时对一个向量里的多个元素做同样运算。在 SDAA 上，它跑在每颗 SPE 的：
- VPU（Vector Processing Unit）：向量处理单元，只接受向量寄存器 VREG 里的数据，做向量存储/算术/类型转换/比较选择。
- VREG（Vector Register）：向量寄存器，存 floatv16（16 个 float 一捆）这类向量，与 SPM/Global 交换数据。
它与另两种并行的关系（容易混）：
- SPMD（线程级）：跨 SPE 的数据并行——每个 SPE 干不同数据。
- SIMD（指令级 / ILP）：单 SPE 内一条指令算 16 个元素——单 SPE 内的数据并行。
- ACE/FU（矩阵乘）：另一条硬件路径（矩阵乘单元），不是 SIMD。
所以 SIMD 是计算屋顶里"向量化"那部分，用来把标量循环变成一条吃 16 个元素的指令。

2. P0/P1 双发模型（SIMD 的关键机制）
c-quarter-reduce-fp32 pattern 给出硬件事实：
P0 管向量计算（如 fp32 向量加，5 周期）；P1 管 LDM 向量装载/存储（load ≥5 周期、store ≥4 周期）。
双发只在 P0/P1 独立指令交错时生效。所以 SIMD 不是"写完向量循环就快"，而是要让 load/store（P1）和 add（P0）穿插起来，用足够的独立向量盖住 load-use 延迟。

```

```bash

性能瓶颈分析：

1. 根本没向量化（标量瓶颈）
最基础：还在用标量循环，直接损失 ~15x。任何 elementwise/reduce 热路径第一步就是上 simd_load/store + 向量运算。

2. 向量寄存器压力（最核心的 SIMD 专属瓶颈）
T1 只有 32 个架构向量寄存器。展开（unroll）越多，同时存活的 floatv16 越多：
- c-quarter-reduce 实测：4x unroll ≈ 8 个显式 floatv16 存活 → 12.04ms（5.7 TFLOPS）。
- 8x unroll ≈ 16 个存活 → 12.28ms，反而更慢（寄存器压力导致 spill / 调度退化）。
- 教训：unroll 不是越大越好，要在"盖住延迟"和"寄存器不爆"之间取平衡。这是 SIMD 优化最容易踩的反直觉坑。

3. 对齐 / 尾处理约束
- simd_load/store 需 64B 对齐；不对齐得用 simd_loadu（unaligned），可能更慢或不保证。
- 长度不是 16 的倍数时必须保留标量尾处理（scalar_tail()），否则越界或漏算。

4. P0/P1 没交错 → 双发没生效
若代码写成"先全 load、再全 compute、再全 store"，P0/P1 无法并行，load-use 延迟暴露，SIMD 吞吐打折。要像 pattern 里那样 4 路独立累加器交错，给编译器排布双发的空间。

5. SIMD 太快 → 反被 DMA 饿着（与访存耦合）
SIMD 把计算压得极快后，常出现"算完了，下一笔数据还没 DMA 到"。此时 SIMD 在等数据 → 实际退化成访存瓶颈。这正是前面 DMA 双缓冲要解决的：用非阻塞 DMA + 双缓冲喂饱 SIMD。所以 SIMD 瓶颈常常不是 SIMD 本身，而是它把上游访存暴露成了瓶颈。

6. 类型/精度宽度
fp16 与 fp32 的向量宽度不同（floatv16 对 fp32 是 16、对 fp16 是 32），类型转换（cast）本身有 cost；做 epilogue/activation 时要算清宽度与转换开销。


```

3. 分块不是越大越好

```bash

1. 是什么
大矩阵计算 C[M,N]=A[M,K]·B[K,N] 不能整块塞进片上，要切成小块迭代：
- M_TILE / N_TILE / K_TILE（或 M2/N2/K2）：每个 SPE 一次算的小块尺寸。
- 分块的目的：让 A/B/C 小块能放进 LDM（片上，≤235KB），并在小块内复用数据（A 的一行块被 N 方向多次用、B 的一列块被 M 方向多次用），减少重复搬运。

```
```bash

性能瓶颈：

1：核心 occupancy 掉下来（idle SPE）
ace-west-mtile-occupancy 失败案例：M-only 切分时，块数 m_blocks = ceil(M / M_TILE)。
选 M_TILE=80 → ceil(2048/80)=26 < 32 个 SPE → 有 6+ 个 SPE 没活干（或尾部不均）。
结果：L3 精度通过，但性能回退 166.5M → 170.1M cycles。
本质：tile 大了 → 块数少于 SPE 数 → 并行度/occupancy 瓶颈（计算能力没喂满）。这正是前面说的"访存计算之外"的第三类瓶颈。

2：LDM 容量反噬，逼小 K2（触发访存/计算二次瓶颈）
ab-double-buffer-k2-regression 失败案例：想加 A/B 双缓冲需要 2×A+2×B+C+缓冲，LDM 放不下 → 被迫把 K2 从 512 缩到 256/416。
K2 变小 → K 方向 macro 迭代变多 → 放大 C 的 RMA reduce + HBM C 读改写流量。
实测：基线 K2=512 单缓冲 54.6ms；K2=256 双缓冲 61.3ms（回退）；K2=416 双缓冲 56.0ms（仍回退）。
本质：tile 大了 → LDM 不够 → 牺牲另一个维度（K2）→ 资源约束瓶颈传导成访存/计算瓶颈。

3：尾部不均衡 + 对齐浪费
若 M % M_TILE != 0，最后一块是残块，要么用 mask/predication 算（浪费），要么分给个别 SPE 造成负载不均（坑 1 里 balance_ok 检查的就是这个）。
tile 尺寸还影响 bank/寄存器压力，过大同样拖累调度。

```

4. ACE / 矩阵乘单元（FU）

```bash

1. 是什么
ACE 是 SPE 内的 FU（Function Unit）矩阵乘单元，专门吃 C[M,K]=A[M,K]·B[K,N] 这种矩阵乘，和 SIMD（VPU 向量路径）是两条独立硬件。它只接收 SPM 里的数据，结果写回 SPM。
接口形态：north/west layout，主循环 issue_ace_gemm_tile(a,b,c) + rt_ace_writeback。
约束：N2（north 宽度）通常取 32，K2 取 32 的倍数（如 512）。当 localbn > 32 时必须先 Permute 重排（见第 6 条）。

```
```bash

性能瓶颈分析：
West M_TILE occupancy（ace-west-mtile-occupancy，失败）：M_TILE 往 128 提虽提升单 SPE ACE 行利用率，但 ceil(M/M_TILE) 可能 < 32 SPE，SPE 空闲 → 166.5M→170.1M cycles 回退。属 occupancy 瓶颈。
LDM 反噬 K2（ab-double-buffer-k2-regression，失败）：为加双缓冲缩小 K2（512→256），K 迭代变多、放大 C 流量 → 54.6→61.3ms 回退。属 资源→访存瓶颈。
归类：ACE 属计算屋顶；瓶颈多为 occupancy 与 LDM 约束，不是纯算力。

```

5. Broadcast(广播)

```bash
1. 是什么
同一行/列方向的多个 SPE 会重复用到同一块 A 或 B。Broadcast 改为"一核读一次、再广播给同行/列其余 SPE"，避免每个 SPE 各自从 Global 重读。
teco-al-gemm.md：GEMM 在 bm/bn/bk 遍历时，按矩阵形状动态适配行列广播方向。

```
```bash

性能瓶颈分析：
它是 GEMM 最大单步收益之一：实测 Matmul 分支 177us → Broadcast 90us（几乎腰斩），因为把"每 SPE 重复读共享块"的 HBM 流量砍掉。
若不做广播 = 访存瓶颈：N 方向扫多个 tile 时，A 块被重复搬 N2 次，HBM 带宽先被打满。
约束：广播方向需随 shape/SPE 组特征动态选；否则可能广播了本不需共享的数据，徒增 RMA/同步开销。
归类：访存屋顶（减少重复搬运量）。

```

6. RMA(核间通信)

```bash
1. 是什么
RMA 是跨 SPE 的 SPM↔SPM 通信（DMA 不支持跨核）。典型用法：split-K 后各 SPE 持有 partial C，需跨核交换做 reduce。
2d-splitk-c-rma-reduce：32 SPE 映射 4×8，K 拆 4 行、M 拆 8 列；每 SPE 算完把 C 切成 4 个 M-quarter，Own 一个、RMA 收另外 3 个同列 quarter，本地 reduce 后写回。用 __rt_local_rply/__rt_remote_rply 做异步 reply。

```
```bash
性能瓶颈分析：
split-K 必带 RMA reduce：不分 K 则每核只有 partial sum，无法得到最终 C——RMA reduce 不是可选项。
实测收益大：70.5ms → 54.6ms（1.258 TFLOPS）。
坑：用普通 volatile int 做远端 reply 会出错；跨 K1 宏块若仍经 HBM C 累加，须保留"读前 C"条件；buffer ownership 不清会写覆盖。
归类：访存/同步屋顶（核间数据交换带宽与正确性）。

```

7. split-K / workspace partial-C

```bash
1. 是什么
split-K：把 K 维拆给多核并行（如 4 行），每核算一部分 K 的 partial C，再汇总。解决"单核 K 太长"或"想喂满更多 SPE"。
workspace partial-C（未来候选，尚未独立验证）：把 partial C 暂存到 workspace，避免每轮都去 HBM 对 C 做 read-modify-write。

```
```bash
性能瓶颈分析:
split-K 的代价是 reduce 流量：拆得越细，C RMA reduce + HBM C 回写越频繁。ab-double-buffer-k2-regression 里 K2 缩小就放大了这股流量导致回退——说明 split-K 收益要与 C 侧代价一起算。
workspace 的价值：消除 HBM C 反复 rmw 的写放大，是 split-K 之后的下一步（pattern 列为 future candidate，需单点验证）。
归类：计算屋顶（喂满多核）+ 访存屋顶（C 回写流量）。
```

8. B row-ring / panel sharing

```bash
1. 是什么
在 ROWS×COLS 网格里，同一行的 COLS 个 SPE 共享 B 宏面板：每个 cid 只从 HBM  Loading 一次本地 B 面板，算完通过 row-local RMA 转发给 cid-1、从 cid+1 收下一块，循环 COLS 次吃完所有 N 面板。
b-row-ring-panel-sharing：ROWS=4,COLS=8,M2=96,N2=32,K2=512；映射 (cid+step)%COLS。

```
```bash
性能瓶颈：

实测：A reuse 28.3ms → B row-ring 20.1ms（3.412 TFLOPS）——把"每 N2 tile 都重读 B"变成"一行只 Load 一次 + RMA 环传"。
坑（多）：n_col 映射写错(cid-step)、把 B 发进 ACE 正在读的缓冲、reset reply 前没做 row-sync 会 race、把 B ring 与 C reduce/workspace 混改导致归因不清、对 N 尾块套全 COLS ring（需 fallback）。
归类：访存屋顶（B 复用，减 HBM 读）。
```

9. Permute（重排）

```bash
1. 是什么
ACE 对 localbn 维度有布局约束：当 N2 > 32 时必须先对 B/C 做数据重排才能喂 ACE，算完 C 还要重排回目标 layout。
是接入 ACE 矩阵的强制前置/后置开销，不是加速本身。

```
```bash
性能瓶颈：
它不是纯收益：重排本身消耗 LDM 与周期。所以 teco-al-gemm.md 强调"接入 Matmul 单元≠纯收益"，要提前规划重排开销。
N2 卡 32 是平衡点：pattern 普遍取 N2=32 恰好避开重排（如 split-K 用 N2=32），正是为避开 Permute 成本。
若 tile 宽度不得不 >32：重排 + 反重排的代价可能吃掉 ACE 加速，需 benchmark 验证。
归类：资源/调度开销，是计算路径上的"税"。

```

10. pipeline fill/steady/drain
```bash
1. 是什么
比"双缓冲"更完整的流水视角：把 kernel 主循环分成 fill（预热装载）→ steady（装载与计算稳定重叠）→ drain（收尾写出） 三阶段，核心是 stage overlap 与 wait/sync 的精确摆放。
b-row-ring-forward-overlap 是实例：ACE 一消费完当前 B 就立刻发 row-ring RMA，等到 ACE writeback 之后、C reduce 之前再 wait——让 RMA 与计算重叠。

```
```bash
性能瓶颈：
只有 steady 才有真重叠：ab-dma-double-buffer-ace-gemm 明确——若 K 方向只有 1 个 tile，双缓冲只剩 fill/drain 开销、没有 steady 重叠，白做。
wait 摆错位置 = 退化串行：B RMA 若在 ACE 消费前发 → 源缓冲被覆盖/误转发；若与 C reduce 共用 reply 字且顺序错 → hang 或错同步。
实测（v15）：5.356ms → 5.168ms，靠的就是把 B RMA 的 issue/wait 重新排序、与 ACE/写回重叠，且不新增 LDM（复用两块 B 缓冲）。
归类：计算/访存屋顶的延迟隐藏（流水），属调度类瓶颈。

```
